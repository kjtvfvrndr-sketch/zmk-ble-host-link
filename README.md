# zmk-ble-host-link

Параметры Bluetooth-соединения с компьютером (хост-линк) для ZMK:

- **автоматически** подбирает для каждого хоста самый быстрый интервал, который он принимает, и latency к нему;
- **запоминает** результат и запрашивает его при каждом следующем подключении;
- позволяет **вручную** закрепить любой параметр для BLE-профиля — для опытов без перепрошивки;
- выводит **интервал отчётов трекбола по BLE** из полученного интервала хоста.

Сделано под Ergohaven K:04 Micro (ZMK v0.3.0 / Zephyr 3.5, трекбол PMW3610 на central), но от платы не зависит.

## Единицы

Как в Bluetooth и ZMK (`BT_PERIPHERAL_PREF_MIN_INT`, `ZMK_SPLIT_BLE_PREF_INT`):

| Параметр | Единица | Пример |
|---|---|---|
| Интервал хоста | 1,25 мс | 6 = 7,5 мс, 9 = 11,25 мс, 12 = 15 мс |
| Latency хоста | события соединения | 30 |
| Timeout | 10 мс (в печатном отчёте) | 410 = 4,1 с |
| Отчёты шара по BLE | мс | 8 |

Лог пишет интервалы в миллисекундах. Каждый запрос подписан, что это: `Asking for search: the fastest interval:`, `…fallback candidate 2`, `…a latency step`, `…back on the best found`, `Asking for the stored search result:`, `…the fallback`, `…undoing someone else's change`, `…asked again by a key` и т. д. С `ZMK_BLE_HOST_LINK_LOG_LEVEL_DBG` при каждом подключении пишется ещё и то, что сохранено для профиля (флаги, сохранённый и запасной результаты, счётчик отказов, потолок latency), а в поиске — опоздавшие ответы, принятие сниженной хостом latency и возвраты соединения на лучший результат.

## Подключение

`config/west.yml`:

```yaml
    - name: zmk-ble-host-link
      remote: kjtvfvrndr-sketch
      revision: main
```

Раскладка:

```c
#include <behaviors/ble_host_link.dtsi>
#include <dt-bindings/zmk/ble_host_link.h>
```

Модуль включается сам, как только раскладка ссылается на `&ble_host_link`. В сборке со Studio он включён всегда: сниппет Studio сохраняет все поведения. На split-периферии не собирается.

Необязательные зависимости, которые модуль находит сам:

- **Отчёты шара** — форк `zmk-pmw3610-driver` с `<zmk_pmw3610_alt/report_interval.h>` (маркер `CONFIG_PMW3610_ALT_REPORT_INTERVAL_RUNTIME`). Без него команды `BALL_BLE_REPORT_*` пишут предупреждение.
- **Индикация** — форк `zmk-rgbled-widget` с `rgbled_widget_blink()` (маркер `CONFIG_RGBLED_WIDGET_BLINK_API`). Без него модуль работает молча.

## Команды

Все действуют на **активный** BLE-профиль и сохраняются для него.

| Команда | Что делает |
|---|---|
| `BLE_HOST_INTERVAL_NEXT` / `_PREV` | Шаг по пресетам интервала хоста, закрепляет значение |
| `BLE_HOST_INTERVAL_SET n` | Закрепить ровно `n` |
| `BLE_HOST_INTERVAL_SET BLE_HOST_INTERVAL_RANGE(min, max)` | Закрепить диапазон (для правил Apple); принятым считается только `min` |
| `BLE_HOST_INTERVAL_SET BLE_HOST_INTERVAL_AUTO` | Вернуть интервал автомату |
| `BLE_HOST_LATENCY_NEXT` / `_PREV` | Шаг по пресетам latency |
| `BLE_HOST_LATENCY_SET n` / `BLE_HOST_LATENCY_AUTO` | Закрепить latency / вернуть автомату |
| `BALL_BLE_REPORT_NEXT` / `_PREV` | Шаг по пресетам отчётов шара по BLE |
| `BALL_BLE_REPORT_SET n` / `BALL_BLE_REPORT_AUTO` | Закрепить / выводить из интервала хоста |
| `BLE_HOST_LINK_AUTO` | Снять все закрепления профиля, забыть всё о хосте и искать заново |
| `BLE_HOST_LINK_REQUEST_AGAIN` | Отправить текущий запрос ещё раз, без изменений и без учёта памяти поиска (профилю, который ничего не просит, — собственные параметры хоста) |
| `BLE_HOST_LINK_SHOW` | Показать на светодиоде, совпадает ли соединение с запрошенным, затем отсчитать значения |
| `BLE_HOST_LINK_TYPE_REPORT` | Напечатать отчёт в активное текстовое поле |

`NEXT/PREV` ходят по списку пресетов узла поведения. `_SET` ставит точное значение вторым параметром. Удобнее всего его использовать из ZMK Studio: значение в привязке клавиши можно поменять на лету и сразу нажать.

**Закреплённая latency** уходит хосту как есть — в поиске тоже, — ограниченная только спецификацией (timeout должен перекрывать два периода прослушивания), но не правилами Apple: так их можно проверить.

**Ручные опыты на Маке.** Закрепляя интервал, закрепляй и latency не выше 30. Если оставить latency на автомате, модуль подставит целевую для этого интервала: столько, чтобы период прослушивания был около 465 мс, по верхней границе запроса (`RANGE(9, 21)` даёт 16, ровно 9 — 40, ровно 6 — 61), а для хоста, уже признанного Apple, — не больше 30. Пока хост не признан, Мак может отказать из-за latency, а не из-за интервала. Лог при отказе помечает поле, которое не совпало: `(asked otherwise)`.

Пресеты по умолчанию (`dts/behaviors/ble_host_link.dtsi`) переопределяются в раскладке:

```dts
&ble_host_link {
    ble-host-interval-presets = <BLE_HOST_INTERVAL_AUTO 6 9 12>;
    ble-host-latency-presets  = <BLE_HOST_LATENCY_AUTO 0 30 60>;
    ball-ble-report-presets   = <BALL_BLE_REPORT_AUTO 4 8 12 16>;
};
```

## Печатный отчёт

Печатаются только цифры, `-`, `_`, `(`, `)`. Эти клавиши дают один и тот же символ в латинской и кириллической раскладках Windows и macOS, так что отчёт читается при любой раскладке компьютера.

```
согласовано(запрошено)_согласовано(запрошено)_согласовано(запрошено)_шар
интервал                latency                 timeout                 отчёты
```

| Ситуация | Строка |
|---|---|
| Мак принял 15–15 | `12(12)_30(30)_410(410)_8` |
| Мак отказал | `12(12)_0(30)_410(410)_8` |
| Мак принял кандидата 11,25–26,25 мс | `9(9-21)_30(30)_410(410)_8` |
| Windows приняла 7,5 мс | `6(6)_61(61)_410(410)_4` |

Пока профиль не подключён, согласованные значения — `0`. Согласованный timeout может отличаться от запрошенного на 1 (`411(410)`): так уходит запрос, который Zephyr иначе не отправил бы (см. ниже). Хост вправе выставить и свой timeout — принятым запрос это не делает и не отменяет.

## Индикация

1. **Отсчёт** — номер пресета в списке, столько же морганий. Фиолетовый — интервал, оранжевый — latency, жёлтый — отчёты шара. Значение вне списка показывается одним длинным морганием.
2. **Ответ хоста**:
   - **синий** — соединение идёт ровно с запрошенным: интервал равен нижней границе запроса, latency совпадает;
   - **красный ×2** — хост отказал, промолчал или выбрал другое;
   - **бирюзовый** — профиль не подключён (значение сохранено и будет запрошено при подключении) или начат поиск.

Ответ на изменение клавишей приходит через `ZMK_BLE_HOST_LINK_APPLY_AFTER_LAST_KEY_MS` (0,5 с) после последнего нажатия: серия нажатий даёт один запрос. Автоматический поиск после подключения ничего не показывает и пишет только в лог. Поиск, запущенный `BLE_HOST_LINK_AUTO`, начинается с бирюзового и заканчивается синим или красным.

`BLE_HOST_LINK_SHOW` сначала показывает ответ хоста, потом отсчёты: если очередь светодиода переполнится, потеряются отсчёты, а не ответ. Сборка проверяет, что пресетов не больше, чем помещается в очередь (16 миганий вместе с ответом).

Цвета задаются `CONFIG_ZMK_BLE_HOST_LINK_LED_RGB_*`.

## Как работает поиск

Каждый запрос проверяется по тому, что соединение реально использует после ответа. **Принятым считается только интервал, равный нижней границе запроса, при той же latency.** Диапазон модуль просит лишь там, где этого требуют правила Apple, и хочет он его нижнюю границу; хост, взявший что-то выше, не дал запрошенного. Latency сравнивается потому, что отказ оставляет соединение на прежних параметрах, а они могут совпасть по интервалу: Мак держит 15 мс при latency 0. Timeout не сравнивается: хост вправе выставить свой, а любой действующий timeout и так соответствует спецификации для своей latency.

Порядок запросов (`src/search.c`):

1. **Безопасный запрос**: ровно `SLOWEST_INTERVAL` (15 мс) при latency 30. Его принимает любой хост, включая Apple. После этого любой отказ ничего не портит: соединение остаётся на этих параметрах.
2. **Самый быстрый интервал, ровно**: 7,5–7,5 мс при latency 30. Диапазоном не спрашивается: Windows из диапазона ленится и берёт верхний край.
3. **Если он отклонён** — хост считается играющим по правилам Apple. (Если сохранённый результат хоста — именно 7,5 мс, отказ в перепоиске этого не делает: он мог быть случайным.) Перебираются запасные кандидаты:
   - диапазоны шириной 15 мс от 11,25 мс (исключение Apple для HID): 11,25–26,25, 12,5–27,5, 13,75–28,75 мс — принятым считается только нижняя граница;
   - затем точные 8,75 … 13,75 мс — для редкого хоста, который не берёт 7,5, но берёт, скажем, 8,75.

   Первый принятый кандидат — результат. Если хост выбрал не нижнюю границу, соединение сразу возвращается на лучший найденный запрос.
4. **Latency** при найденном интервале (тот же запрос интервала, диапазон остаётся диапазоном). Цель — чтобы в простое клавиатура слушала эфир около раза в `IDLE_LISTEN_PERIOD_MS` (465 мс = 15 мс × 31). Это latency 61 при 7,5 мс и 40 при 11,25 мс. Сначала запрашивается цель, при отказе — половинное деление, до 3 шагов. Для хоста по правилам Apple latency ограничена ими (≤ 30). Клавиши и отчёты шара latency не задерживает: данные к отправке её снимают.

**Почему запрос иногда уходит с timeout на 10 мс больше.** Zephyr не отправляет запрос, если соединение уже ему удовлетворяет в его смысле: интервал где-то в диапазоне, latency и timeout равны. Диапазон кандидата Apple всегда содержит текущие 15 мс, и без сдвига timeout запрос не ушёл бы. В сохранённый результат сдвиг не попадает.

**Хост, уводящий соединение во время поиска.** Если хост сам переводит соединение с лучшего найденного запроса на свои параметры, модуль возвращает лучший. Но не бесконечно: если хост увёл соединение второй раз подряд — без ответа на запрос поиска между уходами (ответ — это принятие, отказ, при котором соединение осталось как было, или опоздавший ответ на прежний запрос; молчание ответом не считается), — поиск заканчивается на том, что найдено (результат сохраняется), а соединение остаётся там, куда его увёл хост, до переподключения или до твоего запроса клавишей: модуль его больше не возвращает. Уходы, между которыми поиск продвинулся (хост изредка меняет параметры сам — например, когда у него заработало другое Bluetooth-устройство), не складываются: поиск идёт до конца, число его запросов и так ограничено. Смену параметров ZMK Studio (её параметры, и хост подписан на неё) модуль тоже возвращает, но хосту не засчитывает — до трёх раз за поиск, дальше и такие смены считаются уходами хоста, чтобы поиск заканчивался при любом поведении окружения. Запрос, который ждал повторной отправки, ещё не побывав в эфире, и стал не нужен (соединение надо сначала вернуть), шага поиска не тратит: после возврата он уходит снова. Запрос, уже побывавший в эфире, повторяется как есть: хост ещё может на него ответить. Опоздавший ответ, пришедший, пока поиск ещё идёт — в том числе в паузе перед его последним шагом, — учитывается в результате; пришедший позже считается обычной сменой параметров хостом (см. ниже) — и возвращается на найденное, даже если был лучше. Для этого ответ должен опоздать больше чем на ~5 с, на практике это редкость. Поиск, запущенный клавишей, показывает синий, только если соединение в конце стоит на найденном.

**Хост, снизивший latency.** Если хост дал запрошенный интервал, но выставил latency ниже запрошенной (так умеют Android и Linux), интервал считается принятым при latency хоста. Отличить это от отказа можно только по тому, что соединение изменилось: отказ оставляет его как было.

**Latency 0 от хоста — всегда хуже.** При latency 0 клавиатура слушает эфир на каждом событии соединения, и более быстрый интервал только чаще её будит. Поэтому если хост на запрос с latency ответил latency 0, такой результат проигрывает любому другому, каким бы быстрым он ни был, а из двух таких лучше более медленный интервал. После такого ответа поиск заканчивается (соединение сперва возвращается на лучший найденный): всё более быстрое хост дал бы тоже при 0. Так хост, ставящий latency 0 всему, остаётся на безопасных 15 мс. Latency 0, которую просит сама клавиатура — закреплённая вручную (`BLE_HOST_LATENCY_SET 0`), под выученным потолком latency 0 или при `LATENCY_WHILE_SEARCHING_INTERVAL=0`, — сравнивается как любая другая: там быстрее — лучше. Сохранённый результат помнит, чья это была latency 0, и повторный поиск сравнивает с ним по тому же правилу. Результат с latency 0 на интервале быстрее 15 мс, сохранённый прошлыми версиями (до этого правила), при загрузке сбрасывается, и хост ищется заново (а если поиск на нём выключен обрывами — запрашиваются безопасные 15 мс).

**Опоздавший ответ.** Молчание до срока считается отказом, но если хост ответил позже — соединение перешло на тот запрос, пока уже ждали ответа на следующий, — это засчитывается как принятие того запроса, а то, что было записано из-за молчания (самый быстрый отклонён, кандидат опробован), отменяется. Опоздавшим ответом считается только точное совпадение с запросом: если хост сам перешёл на тот же интервал со своей latency (например, 0), это не ответ, а его собственная смена параметров — иначе сохранился бы результат, при котором клавиатура в простое слушает эфир каждые 7,5 мс.

**Если хост ничего не принял** (например, Apple, растягивающий 15–15 до 30 мс), на следующих подключениях модуль ничего не просит и оставляет хосту его собственные параметры: повторный запрос сделал бы только хуже. Собственными считаются те, с которыми хост открыл соединение, или те, на которые он сам перешёл, пока модуль ещё ничего не просил. Если соединение с них ушло по чужой воле — фоновый набор неактивного профиля, ZMK Studio, — модуль при возврате просит их обратно. Во время самого поиска соединение может остаться на том, что дал хост, до переподключения. SHOW для такого профиля показывает синий, печатный отчёт — `0` в запрошенном.

**Одиночный запрос и чужое изменение.** Если соединение сдвинулось, но не на запрос и не осталось прежним (например, сразу после переключения на хост, ждавший на фоне, первым срабатывает ещё стоящий в очереди фоновый запрос), это не ответ: модуль ждёт настоящего до срока. В поиске такой ответ так же остаётся «без ответа»; запрос, ушедший в момент опоздавшего ответа на предыдущий, тоже ждёт своего.

**Запрос, который не удалось отправить** (контроллер занят другой процедурой на этом соединении или на соединении половин): повтор трижды через 0,3 с и трижды через 5 с, потом операция прекращается без выводов о хосте.

**Первые 5 с соединения** (`BT_CONN_PARAM_UPDATE_TIMEOUT`) Zephyr придерживает запросы и отправляет их потом сам, никому не сообщая о неудаче. Поэтому модуль сам ждёт конца этих 5 с и шлёт запрос сразу — тогда ошибка видна.

**Предохранители поиска:**

- между запросами пауза `PAUSE_BETWEEN_PROBES_MS` (5 с) — Zephyr для собственных повторов держит такую же; после запроса, на который соединение перешло, — не меньше окна учёта обрыва (timeout + 2 с), чтобы обрыв в нём относился только к этому запросу;
- запрос уходит только после `INPUT_QUIET_BEFORE_PROBE_MS` (1 с) без нажатий и движения шара;
- не больше `MAX_PROBES_PER_CONNECTION` (12) запросов за поиск, возвраты соединения не считаются;
- отклонённые кандидаты запоминаются и при повторном поиске пропускаются;
- ожидание ответа хоста — `HOST_ANSWER_TIMEOUT_MS` плюс два периода прослушивания текущего соединения: на медленном соединении клавиатура слышит ответ только так часто;
- пока идёт поиск, модуль лестницы не пересчитывает связь половин после каждого запроса, а ждёт результата (`zmk_ble_host_link_is_searching()`); смена вывода (USB/BLE) и питания второй половины пересчитываются сразу;
- соединение, сдвинувшееся между запросами (опоздавший ответ, ZMK Studio, сам хост), проверяется сразу, а не со следующим запросом.

**Обрыв после запроса.** Учитывается обрыв, пока ответа ждут, и в течение timeout соединения + 2 с после перехода соединения на запрос (берётся timeout, который соединение реально использует, если хост выставил больше запрошенного) (параметры, которые соединение не держит, рвут его только по истечении timeout; отказанный запрос соединение не менял и ни при чём): после запроса поиска, после последнего запроса законченного поиска и после того, как сохранённый результат вступил в силу. Хост мог отключиться из-за запроса — или просто уснуть, или у него выключили Bluetooth. Причина `0x3B` (неприемлемые параметры) засчитывается сразу. Остальные, включая `0x28` (момент обновления пропущен — это может быть и промах самой клавиатуры, у которой два соединения на одном радио), — только если тот же хост вернулся в течение `DROP_COUNTS_IF_HOST_RETURNS_WITHIN_MS` (30 с): бодрствующий хост, которому не понравился запрос, переподключается сразу, уснувший — нет. Обрыв относится к запросу, на который соединение перешло последним (принятому или с опоздавшим ответом), пока не истекло окно; иначе — к запросу, ответа на который ждут. Засчитанный обрыв не запрещает поиск, а исключает именно тот вид запроса на этом хосте: самый быстрый интервал, конкретного кандидата или latency от той, на которой оборвалось; если этот запрос — сохранённый результат или держал соединение на том же интервале (нижней границе запроса: диапазон и точный запрос с одной нижней границей равны) при latency не выше (сохранённый тогда не безопаснее), сохранённый сбрасывается, и хост ищется заново; если так же совпал запасной результат — сбрасывается запасной, и следующее отказавшее подключение снова ищет с тем, что дал этот обрыв: без этого кандидата, если запрос был кандидатом, с потолком latency, если шагом latency, а для безопасного запроса — только засчитанный обрыв. Для сохранённого результата, вступившего в силу, его latency становится потолком, и хост ищется заново под ним. Два засчитанных обрыва подряд — поиск на хосте выключается до `BLE_HOST_LINK_AUTO`; «подряд» прерывает только запрос, который выдержал своё окно без обрыва (в поиске каждое окно выжидается, так что законченный поиск, где обрывов не было, тоже прерывает). Наше собственное отключение (`0x16`) не считается никогда.

**Память.** Результат поиска записывается во флеш сразу, одной записью на хост. Ручные изменения пишутся с дебаунсом ZMK (`ZMK_SETTINGS_SAVE_DEBOUNCE`), NVS одинаковые данные не перезаписывает. Записи привязаны к адресу хоста. Если слот очистили (`BT_CLR`, `BT_CLR_ALL`) или спарили с другим хостом, значения сбрасываются — сразу, так что и тот же хост, спаренный заново, начинает с чистого листа. Значения, выставленные на пустом слоте, получает хост, который спарится первым. Записи старого формата и записи профилей, которых в сборке больше нет, при загрузке отбрасываются и удаляются со следующей записью настроек (через дебаунс, до 60 с).

**Сохранённый результат при следующих подключениях:**

1. Хосту уходит один запрос с найденными параметрами. Принят — счётчик отказавших подключений обнуляется.
2. Отказ — через `STORED_RESULT_RETRY_MS` (30 с) ещё один: отсекает случайности, например загрузку радио Мака другими устройствами.
3. Снова отказ — запрашивается запасной результат, если он есть, иначе безопасные 15 мс. Счётчик отказавших подключений +1 — не больше раза за подключение, и хранится он во флеше, а не в RAM: пробуждение из глубокого сна — это перезагрузка, и в RAM он бы не пережил ни одного сна.
4. Счётчик дошёл до 2, а запасного нет — поиск заново (и на каждом следующем таком подключении, пока один такой поиск не закончится: прерванный — обрыв, переключение профиля, Studio — не в счёт):
   - нашёл не хуже сохранённого (в том виде, в каком тот запрашивается при текущем timeout) — это новый сохранённый результат, счётчик в 0;
   - нашёл медленнее — это запасной результат, сохранённый остаётся (хост, может быть, просто занят); то, что этот поиск узнал о хосте (отклонённые 7,5 мс, опробованные кандидаты), откладывается и вступает в силу, только если запасной заменит сохранённый;
   - ничего не нашёл — всё остаётся как было, включая память кандидатов: занятый хост её не портит.

   Кандидат или самый быстрый интервал, из которых получен сохранённый результат, при этом перепоиске не помечаются отклонёнными.
5. Счётчик дошёл до 5 — сохранённое отклонено на пяти подключениях подряд: хост изменился. Запасной результат становится сохранённым. Без запасного: если поиск заново уже закончился ничем (или поиск запрещён) — сохранённый результат снимается, и хост остаётся на своих параметрах; иначе — поиск заново. Дальше 5 счётчик не растёт.

Записей во флеш здесь немного: счётчик пишется только при изменении (+1 до 5 или обнуление), с дебаунсом ZMK. Даже хост, чередующий «принял/отказал» на каждом подключении, — это около одной записи на подключение; NVS на 32 КБ выдерживает порядка миллионов таких записей.

**Чужие изменения соединения.** Параметры может поменять ZMK Studio или сам хост. Модуль это замечает и через `RESTORE_AFTER_FOREIGN_CHANGE_MS` (5 с) и паузу в вводе один раз запрашивает то, что действовало: сохранённый результат, запасной, безопасный — или, для профиля, который ничего не просит, собственные параметры хоста. Собственный выбор хоста на соединении, где модуль ещё ничего не просил, становится его собственными параметрами и не откатывается (кроме набора ZMK Studio — он собственным не считается никогда; после того как Studio хоть раз была на соединении, собственные параметры до переподключения больше не обновляются: ответ хоста на закрывающий запрос Studio — не его выбор). Если хост перебил возврат быстрее `FOREIGN_CHANGE_GIVE_UP_MS` (60 с), значит, он делает это сознательно, и модуль оставляет соединение как есть до следующего подключения.

**ZMK Studio по Bluetooth** при открытии просит свой набор (интервал `BT_PERIPHERAL_PREF_*`, latency `ZMK_STUDIO_TRANSPORT_BLE_PREF_LATENCY`), при закрытии — обычный. Studio считается открытой, когда соединение идёт на её наборе и хост подписан на её RPC-характеристику. Пока она открыта, соединение не трогается; идущий поиск прекращается и после закрытия начинается заново (что он успел узнать, не сохраняется). Закрытие модуль видит по смене параметров, а если хост отклонил закрывающий запрос Studio — по исчезнувшей подписке (проверка раз в 30 с). Подписка, которая есть уже в первые 15 с после подключения, — это подписка, восстановленная вместе с сопряжением (браузер мог и не отписаться), а не открытая Studio: она не считается, пока не пропадёт и не появится снова. Если запрос Studio при подключении лёг поверх запроса модуля, модуль один раз повторяет свой; отказ после этого — обычный отказ хоста. Сеанс Studio, переживший переподключение клавиатуры, поэтому идёт на параметрах модуля — медленнее, но работает.

**Только активный хост подключён** (`KEEP_ONLY_ACTIVE_HOST_CONNECTED`, включено по умолчанию). ZMK держит подключёнными все хосты, которые подключились, а ввод получает только активный; остальные зря будят радио и отнимают эфир у активного хоста и у второй половины. С этой опцией:

- как только хост активного профиля подключён, хосты остальных профилей отключаются; ZMK в это время не рекламирует себя, и они не возвращаются;
- пока хоста активного профиля нет (только что выбран профиль, чей хост далеко, или хост ушёл), ZMK рекламирует себя всем. Хосты других профилей не отключаются — иначе переподключались бы снова и снова, — а получают фоновый набор: 60–75 мс, latency 25, timeout 6 с, то есть одно пробуждение радио примерно раз в 2 с. Так и прежний активный хост при переключении: он остаётся на фоне до подключения выбранного.

Переход на профиль, чей хост был отключён, — это переподключение, обычно 1–3 с; на хост, ждавший на фоне, — сразу, а его сохранённые параметры применяются за несколько секунд (на фоновом наборе клавиатура слышит ответ хоста реже). Соединение, переставшее быть активным, модуль забывает: при возврате на его профиль параметры применяются заново, а прерванный переключением поиск начинается сначала. Хост, который не принадлежит ни одному профилю (идёт сопряжение на пустом слоте), не трогается. Фоновый запрос тоже ждёт конца первых 5 с нового соединения, а если не ушёл (контроллер занят), повторяется через 5 с, не больше трёх раз. Ранний сон модуля лестницы и сон ZMK от неактивных хостов не зависят.

**Отчёты шара** при автомате равны половине интервала хоста, округлённой вверх до сетки кадров сенсора (4 мс): 7,5 мс → 4 мс, 8,75–15 мс → 8 мс. Действуют только при выводе по BLE; на USB работает `PMW3610_ALT_REPORT_INTERVAL_MIN_USB`.

## Проверка логики без железа

```sh
make -C tests
```

Два набора. `search_test` прогоняет поиск против моделей хостов, `decisions_test` — таблицы решений вокруг поиска (`src/decisions.c`): сценарии отказов сохранённого результата подключение за подключением (занятый хост, изменившийся хост, прерванный перепоиск, перепоиск без результата, запрет поиска), что меняет законченный поиск, какие обрывы засчитываются, что они меняют и к какому запросу относятся, когда Studio владеет соединением. Логика в `ble_host_link.c` — это только связь этих решений с Bluetooth.

Поиск прогоняется против моделей хостов:

- Мак строго по правилам;
- Мак с исключением для HID, выбирающий нижний или верхний край диапазона (верхний — отказ);
- Мак, оставляющий текущий интервал;
- Apple, растягивающий 15–15 до 30 мс;
- Windows-подобные хосты, выбирающие нижний или верхний край;
- хост, не дающий меньше 11,25 мс;
- хосты с лимитами latency;
- хост, отказывающий во всём;
- хост, принимающий только 7,5 мс;
- хост, сам снижающий latency до 20.

Отдельно проверяются: память о кандидате и о самом быстром интервале сохранённого результата, потолок latency после обрыва, ленивый Windows (только точные запросы, не больше 3), опоздавший ответ на 7,5 мс (и во время запроса, и в паузе, и во время возврата), чужое изменение соединения раньше настоящего ответа, отказы через Link Layer (с ответом, а не молчанием), хост до 30 мс с почти полной маской кандидатов, закреплённая latency без ограничений Apple и сдвиг timeout.

Проверяется, что соединение всегда кончает на лучшем найденном запросе, никогда не медленнее 15 мс, что лучший интервал — нижняя граница запроса и что лимит запросов соблюдается. Раннер повторяет поведение Zephyr: запрос, который соединение уже выполняет в его смысле, не уходит.

## Про хосты

- **Apple** (QA1931):
  - нижний край интервала ≥ 15 мс и кратен 15;
  - верхний ≥ нижний + 15 мс (кроме ровно 15–15);
  - latency ≤ 30;
  - интервал × (latency + 1) ≤ 2 с;
  - timeout 2–6 с;
  - для HID до 11,25 мс «может быть принято».

  Отсюда безопасный старт 15–15 и кандидаты поиска. Некоторые устройства Apple сами растягивают 15–15 до 30 мс; поиск это видит (отказ), но спорить не будет.
- **Windows и Linux** обычно дают 7,5 мс на точный запрос. Из диапазона Windows берёт верхний край, поэтому поиск спрашивает точными значениями. Какую latency они принимают, поиск выясняет сам.
- Хост может позже поменять параметры сам. Модуль один раз возвращает свои; если хост настаивает — оставляет до следующего подключения или до запроса клавишей, который хост принял (в том числе запасного результата, на который модуль сам перешёл после отказа хоста на запрос клавиши).
