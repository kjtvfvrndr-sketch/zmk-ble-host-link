# zmk-ble-host-link

Параметры Bluetooth-соединения с компьютером (хост-линк) для ZMK:

- **автоматически** подбирает для каждого хоста самый быстрый точный интервал, который он принимает, и latency к нему;
- **запоминает** результат и запрашивает его при каждом следующем подключении;
- позволяет **вручную** закрепить любой параметр для BLE-профиля — для опытов без перепрошивки;
- выводит **интервал отчётов трекбола по BLE** из полученного интервала хоста.

Сделано под Ergohaven K:04 Micro (ZMK v0.3.0 / Zephyr 3.5, трекбол PMW3610 на central), но от платы не зависит.

## Единицы

Как в Bluetooth и ZMK (`BT_PERIPHERAL_PREF_MIN_INT`, `ZMK_SPLIT_BLE_PREF_INT`):

| Параметр | Единица | Пример |
|---|---|---|
| Интервал хоста | 1,25 мс | 6 = 7,5 мс, 9 = 11,25 мс, 12 = 15 мс |
| Latency хоста | события соединения | 30 |
| Timeout | 10 мс (в печатном отчёте) | 600 = 6 с |
| Отчёты шара по BLE | мс | 8 |

Лог пишет интервалы в миллисекундах. Каждый запрос подписан: `Asking for search: the secure request:`, `…search: a ladder step`, `…search: a latency step`, `Asking for the stored search result:`, `…the latency fixed by hand`, `…the link back on the profile's parameters`, `…asked again by a key`. С `ZMK_BLE_HOST_LINK_LOG_LEVEL_DBG` при каждом подключении пишется и то, что сохранено для профиля (результат, кандидат, порог интервала, потолок latency).

## Подключение

`config/west.yml`:

```yaml
    - name: zmk-ble-host-link
      remote: kjtvfvrndr-sketch
      revision: main
```

Раскладка:

```c
#include <behaviors/ble_host_link.dtsi>
#include <dt-bindings/zmk/ble_host_link.h>
```

Модуль включается сам, как только раскладка ссылается на `&ble_host_link`. В сборке со Studio он включён всегда: сниппет Studio сохраняет все поведения. На split-периферии не собирается.

Необязательные зависимости, которые модуль находит сам:

- **Отчёты шара** — форк `zmk-pmw3610-driver` с `<zmk_pmw3610_alt/report_interval.h>` (маркер `CONFIG_PMW3610_ALT_REPORT_INTERVAL_RUNTIME`). Без него команды `BALL_BLE_REPORT_*` пишут предупреждение.
- **Индикация** — форк `zmk-rgbled-widget` с `rgbled_widget_blink()` (маркер `CONFIG_RGBLED_WIDGET_BLINK_API`). Без него модуль работает молча. Если в форке есть `rgbled_widget_blink_on_all_halves()` (маркер `CONFIG_RGBLED_WIDGET_BLINK_ON_ALL_HALVES_API`), вспышки модуля видны на всех половинах split: параметры хост-линка — настройка всей клавиатуры.

**ZMK Studio — только по USB.** В ZMK v0.3 Studio по Bluetooth может зависать при подключении; это транспорт ZMK, а не модуль. Модуль её параметры по BLE узнаёт и не трогает (см. ниже), но работать со Studio надёжнее через USB-сборку (`studio-rpc-usb-uart`).

## Команды

Все действуют на **активный** BLE-профиль и сохраняются для него.

| Команда | Что делает |
|---|---|
| `BLE_HOST_INTERVAL_NEXT` / `_PREV` | Следующий больший / меньший пресет интервала, по кругу; закрепляет значение |
| `BLE_HOST_INTERVAL_SET n` | Закрепить ровно `n` |
| `BLE_HOST_INTERVAL_AUTOMATIC` | Вернуть интервал автомату |
| `BLE_HOST_LATENCY_NEXT` / `_PREV` | То же для latency |
| `BLE_HOST_LATENCY_SET n` / `BLE_HOST_LATENCY_AUTOMATIC` | Закрепить latency / вернуть автомату |
| `BALL_BLE_REPORT_NEXT` / `_PREV` | То же для отчётов шара по BLE |
| `BALL_BLE_REPORT_SET n` / `BALL_BLE_REPORT_AUTOMATIC` | Закрепить / выводить из интервала хоста |
| `BLE_HOST_LINK_AUTO` | Снять все закрепления профиля, забыть всё о хосте и искать заново |
| `BLE_HOST_LINK_REQUEST_AGAIN` | Отправить запрос профиля ещё раз: сохранённый результат или закреплённые значения. Во время поиска не действует: в логе `asking again ignored -- a search is running`, бирюзовая вспышка |
| `BLE_HOST_LINK_SHOW` | Показать на светодиоде, идёт ли соединение так, как задумано |
| `BLE_HOST_LINK_TYPE_REPORT` | Напечатать отчёт в активное текстовое поле |

**NEXT/PREV** идут от действующего значения — закреплённого или выбранного автоматом — к ближайшему большему (меньшему) пресету, а после самого большего — к самому меньшему: latency 0 → 30 → 60 → 0. Автомат в круг не входит: значение возвращают ему `…_AUTOMATIC` или `BLE_HOST_LINK_AUTO`.

`_SET` ставит точное значение вторым параметром. Удобнее всего его использовать из ZMK Studio: значение в привязке клавиши можно поменять на лету и сразу нажать. Диапазонов интервала больше нет: только точные значения. Возврат автомату — отдельные команды `…_AUTOMATIC`: Studio умеет редактировать либо диапазон, либо список значений, но не их смесь. Прежняя запись `_SET … _AUTO` (`BLE_HOST_INTERVAL_SET BLE_HOST_INTERVAL_AUTO` и т. п.) в раскладке работает как раньше.

**Закреплённое значение заменяет свою часть запроса, без поиска.** Закреплённый интервал уходит с закреплённой latency или, если она на автомате, с той, что даёт период прослушивания около 465 мс (61 при 7,5 мс, 40 при 11,25 мс, 30 при 15 мс). Закреплённая latency уходит с закреплённым интервалом или с сохранённым результатом; сохранённый результат при её смене не сбрасывается. Если результата ещё нет, поиск идёт на закреплённой latency (без шагов latency), а для сохранения берётся та latency, что выбрал бы автомат.

**Latency ограничивает только спецификация:** timeout (6 с) должен быть больше двух периодов прослушивания, `интервал × (latency + 1) × 2 < timeout`. Больше модуль урезает и пишет в лог, например `latency 200 trimmed to 98: the 6.0 s timeout must outlast two listening periods` (при 30 мс). Хост может ограничивать строже: Windows при 30 мс даёт latency не выше 45 — для закреплённого значения это отказ.

**Закреплённое отклонено.** Через 5 с запрос уходит ещё раз; снова отказ — в логе `the host refused the latency fixed by hand` (или `interval`, `values`), светодиод мигает красным, а хост до следующего подключения остаётся на своих параметрах. Ничего не запоминается: следующее подключение просит снова.

**Ручные опыты на Маке.** Мак на Apple Silicon принимает только ровно 15 мс при latency до 30. Закрепляя интервал, закрепляй и latency не выше 30; иначе отказ может быть из-за latency. Лог при отказе помечает поле, которое не совпало: `(asked otherwise)`.

Пресеты по умолчанию (`dts/behaviors/ble_host_link.dtsi`) переопределяются в раскладке:

```dts
&ble_host_link {
    ble-host-interval-presets = <6 9 12>;
    ble-host-latency-presets  = <0 30 60>;
    ball-ble-report-presets   = <4 8 12 16>;
};
```

## Печатный отчёт

Печатаются только цифры, `_`, `(`, `)`. Эти клавиши дают один и тот же символ в латинской и кириллической раскладках Windows и macOS, так что отчёт читается при любой раскладке компьютера.

```
согласовано(запрошено)_согласовано(запрошено)_согласовано(запрошено)_шар
интервал                latency                 timeout                 отчёты
```

| Ситуация | Строка |
|---|---|
| Мак принял 15 мс | `12(12)_30(30)_600(600)_16` |
| Мак отказал | `12(12)_0(30)_720(600)_16` |
| Windows приняла 7,5 мс | `6(6)_61(61)_600(600)_8` |

Пока профиль не подключён, согласованные значения — `0`. Хост вправе выставить свой timeout — принятым запрос это не делает и не отменяет.

## Индикация

- **синий** — соединение идёт ровно с запрошенным (интервал и latency совпадают);
- **красный ×3** — хост отказал или выбрал другое;
- **бирюзовый** — профиль не подключён (значение сохранено и будет запрошено при подключении) или идёт поиск.

Синий и бирюзовый — по одной вспышке: это базовое подтверждение. На split с форком виджета вспышки видны на всех половинах.

Ответ на изменение клавишей приходит через `ZMK_BLE_HOST_LINK_APPLY_AFTER_LAST_KEY_MS` (0,5 с) после последнего нажатия, когда хост ответил: серия нажатий даёт один запрос. Если хост сначала отказал, ответ — после повтора через 5 с. Отчёты шара хосту не отправляются: их смена сразу мигает синим. Автоматический поиск после подключения ничего не показывает и пишет только в лог; поиск, запущенный `BLE_HOST_LINK_AUTO`, начинается с бирюзового и заканчивается синим или красным.

`BLE_HOST_LINK_SHOW` показывает только это: синий, красный или бирюзовый. Значения можно посмотреть в печатном отчёте.

Цвета задаются `CONFIG_ZMK_BLE_HOST_LINK_LED_RGB_*`.

## Как работает поиск

**Принятым считается только соединение, перешедшее ровно на запрошенное: тот же интервал и та же latency** — первое такое изменение до срока ответа. Хост, давший интервал, но снизивший latency (так умеют Android и Linux), запроса не принял. Timeout не сравнивается: хост вправе выставить свой. Другие изменения параметров до срока ответа ничего не решают (отказ по Link Layer приходит как «обновление» на старые значения, а ещё может сработать чужое обновление), решает срок: `HOST_ANSWER_TIMEOUT_MS` (4 с) плюс два периода прослушивания текущего соединения.

**Опоздавший ответ.** Если соединение перешло ровно на отклонённый запрос позже срока, но до следующего запроса, это принятие.

**Один запрос за раз.** Следующий запрос — поиска, клавиши, `REQUEST_AGAIN` — уходит только после ответа на предыдущий или после его срока. Ответом считается и переход соединения ровно на предыдущий запрос, даже если тот задала уже прерванная операция или он ушёл неактивному хосту: следующий тогда уходит сразу, не дожидаясь срока.

Порядок запросов (`src/search.c`):

1. **Безопасный запрос**: ровно `SLOWEST_INTERVAL` (15 мс) при latency 30. Его принимает любой хост, включая Apple.
2. **Лестница**: точные интервалы от `FASTEST_INTERVAL` (7,5 мс) вверх с шагом 1,25 мс до 13,75 мс, каждый при latency 30. Первый принятый — результат: он самый быстрый из тех, что хост даёт. Отказы соединение не трогают: оно остаётся на безопасном запросе.
3. **Latency** при найденном интервале: цель — чтобы в простое клавиатура слушала эфир около раза в `IDLE_LISTEN_PERIOD_MS` (465 мс = 15 мс × 31): 61 при 7,5 мс, 40 при 11,25 мс, 30 при 15 мс (тогда шага нет). Сначала цель, при отказе — половина пути от принятой, до 3 шагов. Клавиши и отчёты шара latency не задерживает: данные к отправке её снимают.

Результат — последний принятый запрос: ступень лестницы, если какая-то принята, иначе безопасный, иначе ничего. Мак: 15 мс, принято; 7,5 … 13,75 мс — отказ; итог 15 мс / 30, семь запросов. Windows: 15 мс, 7,5 мс, latency 61 — три запроса.

Между запросами — пауза `PAUSE_BETWEEN_SEARCH_REQUESTS_MS` (5 с) после ответа: так же Zephyr разносит свои повторы, и есть время для опоздавшего ответа. После принятого запроса — не меньше окна учёта обрыва (timeout + 2 с). Запрос поиска уходит только после `INPUT_QUIET_BEFORE_SEARCH_REQUEST_MS` (1 с) без нажатий и движения шара. Поиск Мака занимает около минуты.

**Сразу после сопряжения** хост ещё занят новым устройством (Windows ставит драйвер) и может отказать в том, что примет через минуту: Windows отказала в 7,5 мс через 10 с после сопряжения, и профиль сохранил 8,75 мс. Запрос посреди этой настройки может даже заставить Windows разорвать связь и сопряжение. Поэтому на соединении, где хост только что сопрягся, весь поиск, включая первый (безопасный) запрос, начинается не раньше `SEARCH_WAITS_AFTER_PAIRING_MS` (30 с) после сопряжения. В логе: `Profile N's host paired just now: the search starts in N s`.

**Если хост ничего не принял**, сохранять нечего: соединение остаётся на параметрах хоста до следующего подключения, а оно ищет снова.

Пока идёт поиск, модуль лестницы половин не пересчитывает связь после каждого запроса, а ждёт результата (`zmk_ble_host_link_is_searching()`).

**Запрос, который не удалось отправить** (контроллер занят другой процедурой на этом соединении или на соединении половин): повтор трижды через 0,3 с и трижды через 5 с, потом операция прекращается без выводов о хосте.

**Первые 5 с соединения** (`BT_CONN_PARAM_UPDATE_TIMEOUT`) Zephyr придерживает запросы и отправляет их потом сам, никому не сообщая о неудаче. Поэтому модуль сам ждёт конца этих 5 с и шлёт запрос сразу — тогда ошибка видна. Запрос, который соединение уже выполняет, не отправляется вовсе: он принят. Если он продержался своё окно (timeout + 2 с), это прерывает «два подключения подряд» для него, как у отправленного; обрыв в этом окне ему не засчитывается — модуль ничего не менял.

## Сохранённый результат

Хранится одно точное значение: интервал и latency. При каждом подключении хосту уходит один запрос с ним.

1. **Принят** — всё.
2. **Отказ** — через `RETRY_REFUSED_REQUEST_AFTER_MS` (5 с) ещё один: отсекает случайности, например загрузку радио Мака другими устройствами.
3. **Снова отказ** — хост ищется сейчас же, и найденное действует на этом подключении. Для памяти есть второе значение — **кандидат**:
   - нашёл сохранённое — хост был просто занят, кандидат стирается;
   - нашёл то же, что кандидат — кандидат становится сохранённым;
   - нашёл другое — это новый кандидат, сохранённое не трогается;
   - ничего не нашёл — ничего не меняется.

   Если сохранённое потом принято, кандидат стирается.

Так один неудачный вечер не портит результат, а изменившийся хост за два подключения получает новый.

**Память.** Результат поиска записывается во флеш сразу, одной записью на хост; ручные изменения — с дебаунсом ZMK (`ZMK_SETTINGS_SAVE_DEBOUNCE`), NVS одинаковые данные не перезаписывает. Записи привязаны к адресу хоста. Если слот очистили (`BT_CLR`, `BT_CLR_ALL`), в логе `Profile N: bond cleared, values reset`; если спарили с другим хостом — `another host is bonded now`. Значения сбрасываются сразу, так что и тот же хост, спаренный заново, начинает с чистого листа. Значения, выставленные на пустом слоте, получает хост, который спарится первым. Записи прежних версий (другой формат) при загрузке отбрасываются и удаляются со следующей записью настроек: хосты ищутся заново.

## Обрывы после запроса

Параметры, которые соединение не держит, рвут его по истечении timeout. Поэтому обрыв относится к запросу, если случился, пока ждут ответа, или в течение timeout соединения + 2 с (8 с) после перехода на запрос (берётся timeout, который соединение реально использует). Хост мог отключиться из-за запроса — или уснуть, или у него выключили Bluetooth. Обрыв засчитывается запросу, только если:

- **хост вернулся в течение `DROP_COUNTS_IF_HOST_RETURNS_WITHIN_MS` (30 с)**: бодрствующий хост, которому не понравился запрос, переподключается сразу, уснувший — нет (причина `0x3B`, «неприемлемые параметры», засчитывается без ожидания);
- **соединение не рвётся само**: потеря связи в эфире без запроса (`0x08` timeout, `0x28`, `0x3D`, `0x3E`), после которой хост сразу вернулся, помечает хост нестабильным, и обрывы не засчитываются, пока какое-то соединение не продержится `STABLE_LINK_MS` (30 с). Хост, сам закрывший соединение (`0x13` — выключили Bluetooth, удалили сопряжение; `0x15` — выключили адаптер), нестабильным не становится;
- **тот же запрос обвинён на двух подключениях подряд**: «подряд» прерывает запрос, выдержавший своё окно без обрыва.

Закреплённые вручную значения не обвиняются никогда. Наше собственное отключение (`0x16`) не считается никогда.

**Сила сигнала.** С `ZMK_BLE_HOST_LINK_LOG_RSSI=y` (нужен `BT_CTLR_CONN_RSSI=y`) лог показывает RSSI хост-линка при каждом запросе и при `SHOW`, а при обрыве — последнее значение и сколько секунд назад оно прочитано (модуль тихо читает его раз в 30 с): `last host link RSSI -76 dBm, 12 s before the link went down`.

Подтверждённый обрыв: если latency запроса выше 30 (шаг latency) или это 15 мс, его latency становится потолком — дальше просится ниже; иначе интервал запроса и все быстрее пропускаются лестницей. Сохранённый результат или кандидат, которые это исключает, стираются: следующее подключение ищет заново. `BLE_HOST_LINK_AUTO` забывает и это.

## Чужие изменения соединения

Параметры может поменять ZMK Studio или сам хост. Модуль это замечает и через `RESTORE_AFTER_FOREIGN_CHANGE_MS` (5 с) и паузу в вводе один раз просит то, что действовало. Если хост перебил возврат быстрее `FOREIGN_CHANGE_GIVE_UP_MS` (60 с), значит, он делает это сознательно, и модуль оставляет соединение как есть до следующего подключения или до запроса клавишей.

**ZMK Studio по Bluetooth** при открытии просит свой набор (интервал `BT_PERIPHERAL_PREF_*`, latency `ZMK_STUDIO_TRANSPORT_BLE_PREF_LATENCY`), при закрытии — обычный. Studio считается открытой, когда соединение идёт на её наборе и хост подписан на её RPC-характеристику. Пока она открыта, соединение не трогается; идущий поиск прекращается и после закрытия начинается заново. Закрытие модуль видит по смене параметров, а если хост отклонил закрывающий запрос Studio — по исчезнувшей подписке (проверка раз в 30 с). Подписка, которая есть уже в первые 15 с после подключения, — восстановленная вместе с сопряжением, а не открытая Studio: она не считается, пока не пропадёт и не появится снова. Если запрос Studio при подключении лёг поверх запроса модуля, модуль один раз повторяет свой.

## Хосты других профилей

ZMK держит подключёнными все хосты, которые подключились, а ввод получает только активный.

- **Хост, подключившийся, пока активен другой профиль**, один раз получает свои параметры: сохранённый результат (или закреплённые значения, или безопасный запрос). Фоновых параметров нет: экономия на неактивном хосте — единицы мкА.
- **Хост профиля, с которого переключились**, остаётся на том, что у него было.

**Только активный хост подключён** (`KEEP_ONLY_ACTIVE_HOST_CONNECTED`, включено по умолчанию): как только хост активного профиля подключён, остальные отключаются (ZMK в это время не рекламирует себя, и они не возвращаются). Пока хоста активного профиля нет, остальные не отключаются — иначе переподключались бы снова и снова. Хост отключается, только когда его связь спокойна: зашифрована, нет неотвеченного запроса параметров от модуля и прошло 3 с с подключения; через 15 с после первой попытки — в любом случае. Отключение посреди шифрования оставляет хосту неудачное шифрование на его паре, а отключение за незавершённой сменой параметров доходило только через таймаут связи. Хост, ушедший дольше чем за 1 с, виден в логе как WRN.

Переход на профиль, чей хост был отключён, — это переподключение, обычно 1–3 с. Соединение, переставшее быть активным, модуль забывает: при возврате на его профиль параметры применяются заново, а прерванный переключением поиск начинается сначала. Хост, который не принадлежит ни одному профилю (идёт сопряжение на пустом слоте), не трогается.

## Лог подключений хостов

С `ZMK_BLE_HOST_LINK_LOG_HOST_CONNECTIONS` (включено по умолчанию, когда есть лог) модуль пишет в лог, что происходит с соединениями компьютеров. Строки INF появляются только на события Bluetooth; поведение клавиатуры от этого не меняется.

- **Выбор профиля:** `Profile 1 selected: its host is away; hosts connected, by profile: 0`. Состояние — `open, no host paired`, `its host is connected` или `its host is away`. Первая строка после старта — `Profile 0 active: …`.
- **Подключение хоста:** чей это профиль — `Profile 1's host connected while profile 0 is active`, или `A host no profile has connected …`. Строкой ниже — адрес, с которым хост пришёл в эфир, и личность, к которой стек его привязал. Если приватный адрес не узнан: `not resolved to any bonded host`.
- **Шифрование:** `Profile 1's host: encrypted, security level 2` или WRN `encryption failed: key missing (2)`.
- **Отключение:** `Profile 1's host disconnected after 0.3 s: 0x3e, failed to be established`.
- **Сопряжение и связи:** `Host … paired, bond kept`, WRN `pairing failed: …`, `Bond deleted: profile 3's host …` (после `BT_CLR`).
- **Снимок** через 5 с после старта и по `BLE_HOST_LINK_SHOW`:
  - адреса профилей ZMK и есть ли под каждым связь в стеке (`MISSING`, если нет);
  - все связи, которые держит стек: чей профиль, другая половина или ничья;
  - все объекты соединений с состоянием. `disconnected, still held` — объект, который уже не соединён, но никем не освобождён: новые подключения могут упереться в его отсутствие.
- **Причина старта** (нужен `HWINFO`, включается сам): `Started after: reset pin`, `software reset …`, `CPU lockup`, `watchdog`, или `no reset recorded` — включили питание. Запись сбрасывается после чтения, так что каждый старт показывает свою причину.

**Сверка рекламы** (`ZMK_BLE_HOST_LINK_LOG_ADVERTISING_OUT_OF_STEP`, для отладки; включена вместе с логом подключений): ZMK рекламирует клавиатуру — зовёт хосты, — пока активный профиль открыт или его хост не подключён, и сам помнит, идёт ли реклама, не спрашивая стек. Его обработчики подключения и отключения работают в разных потоках; если они пересекутся, ZMK может перестать звать, считая, что зовёт: никто новый подключиться не может, уже подключённые работают, перезапуск лечит. Раз в секунду модуль сверяет правило ZMK с тем, что делает стек. Если они расходятся дольше 3 с — WRN `Advertising out of step for 3 s: …` (в том числе когда реклама идёт, а объекта соединения для ответившего хоста нет); когда сходятся — INF `Advertising back in step …`. В снимке `SHOW` строка `advertising: …`. Если реклама идёт как положено 15 с, а не подключился ни один хост — даже хост другого профиля, который обычно приходит сразу, — WRN `Advertising for 15 s and no host has connected …` и весь снимок `SHOW`, один раз на такой отрезок (так же выглядит и хост, которого просто нет рядом). Пока ни один профиль не сопряжён с хостом, это не проверяется: сам никто прийти не может. Только лог; опция читает внутреннее состояние стека Zephyr.

**Перезапуск рекламы** (`ZMK_BLE_HOST_LINK_RESTART_ADVERTISING_WHEN_NO_HOST_ANSWERS`, для отладки, выключен по умолчанию): после строки «no host has connected» реклама перезапускается через вызов ZMK для смены имени устройства — с тем же именем, поэтому ничего не записывается. Если хост подключится в первые 3 с (так приходит хост, который ждёт рекламу) — INF `A host answered N ms after the advertising was restarted` (реклама застряла, перезапуск её лечит); если позже, до 15 с, — INF `A host came N s after … too late to tell` (скорее всего, его подключили руками, вывода нет); если никто — WRN `Still no host 15 s after …` (сбой ниже рекламы).

**Проверка своей стороны сопряжения** (`ZMK_BLE_HOST_LINK_CHECK_OWN_PAIRING_STATE`, только для отладки): при старте, по `SHOW` и через 1,5 с после неудачного сопряжения клавиатура проверяет, что её закрытый ключ для сопряжения всё ещё соответствует открытому. Стек вычисляет общий ключ с тестовым ключом, модуль — тот же ключ с другой стороны. В логе `Pairing key pair OK (…), public key a1b2c3d4` или WRN `… BROKEN`. С каждым сопряжением печатаются первые байты открытого ключа клавиатуры, а при подключении и неудачном сопряжении — адрес, который стек отдал радиочасти, против постоянного (WRN, если они разные). Опция использует внутренние функции стека Zephyr. Сопряжение, начатое в ту четверть секунды, пока идёт проверка, один раз не пройдёт: стек вычисляет общий ключ по одному.

Так видно, где останавливается хост, который не может вернуться. Ни одной строки на его попытки — радиочасть отбросила их раньше стека. Иначе виден шаг, на котором рвётся: адрес, шифрование или позже.

## Отчёты шара

При автомате — интервал хоста, округлённый вверх до сетки кадров сенсора (4 мс): **один отчёт на событие соединения**. 7,5 мс → 8 мс, 8,75–11,25 мс → 12 мс, 12,5–15 мс → 16 мс. Чаще хост всё равно не заберёт: лишние отчёты копятся в очереди и теряются (рывки, «желе»). Действуют только при выводе по BLE; на USB работает `PMW3610_ALT_REPORT_INTERVAL_MIN_USB`.

## Проверка логики без железа

```sh
make -C tests
```

`search_test` прогоняет поиск против моделей хостов (принимает всё; Мак — только 15 мс; ничего; от 11,25 мс с latency до 40; снижающий latency до 0; latency до 45), с закреплённой latency, порогом интервала и потолком latency, и опоздавшие ответы. `decisions_test` — таблицы решений вокруг поиска (`src/decisions.c`): сохранённое и кандидат, учёт обрывов (два подключения подряд, поздний возврат, нестабильный хост, причины `0x16`, `0x3B`, хост, сам закрывший соединение), что меняет подтверждённый обрыв, к какому запросу он относится, когда Studio владеет соединением. `ble_host_link.c` — только связь этих решений с Bluetooth.

## Про хосты

- **Apple** (QA1931): интервал кратен 15 мс, latency ≤ 30, интервал × (latency + 1) ≤ 2 с, timeout 2–6 с. Mac на Apple Silicon на деле принимает только ровно 15 мс; диапазоны и другие точные интервалы отклоняет. Открывает соединение на 30 мс / 0 и потом сам переходит на 15 мс / 0.
- **Windows** принимает всё, но отвечает медленно (2–4 с) и иногда сначала «отказывает», а через полсекунды применяет — это ловит опоздавший ответ.
- **Android** обычно даёт 7,5 мс. **Linux (BlueZ)** может снижать latency до 0 — по правилу точного совпадения это отказ: такой хост остаётся на своих параметрах, а поиск повторяется при каждом подключении. Закреплённая latency 0 (`BLE_HOST_LATENCY_SET 0`) это решает.
- Хост может позже поменять параметры сам. Модуль один раз возвращает свои; если хост настаивает — оставляет до следующего подключения или до запроса клавишей, который хост принял.
